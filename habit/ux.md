# UX 設計 — 習慣トラッカー

対象: `creations/habit/app.html`(単一HTML / 依存ゼロ / localStorage)
作成: architect 司祭(構築枢機卿 配下) / 2026-08-31
参照: `requirements.md` / `identity.md` / `ux-review.md`

> この文書は「実装がこう動いている」の記述ではない。
> **あるべき体験を先に定義し、実装がそれを満たすかを各節末尾で確認する。**
> 満たしていない項目は「未達」と正直に書く。

## 0. この道具が果たすべき約束

習慣トラッカーは記録装置ではなく **継続を支える装置**である。よって体験の中心はただ一つ:

> **朝、開いて、今日の丸を押す。それが3秒で終わる。**

この一点を守るために、他のすべての機能(追加・編集・ヒートマップ・エクスポート)は
**主動線を邪魔しない位置**へ退く。UX の設計判断はすべてこの優先順に従う:

1. 今日を記録する(毎日・複数回)
2. 続いているかを知る(毎日・一瞬)
3. 過去を振り返る/直す(週〜月に一度)
4. 習慣を増減する(初回と、たまに)
5. データを持ち出す(まれ)

## 1. 主要フロー

### 1-1. 初回起動(データゼロ)

**あるべき体験:** 最初に読むべきものが、最初に目に入る。

| 順 | 見えるもの | 意図 |
|---|---|---|
| 1 | **空状態カード**「まだ習慣がありません」+ 目的の説明 + 一次CTA「最初の習慣をつくる」 | 「これは何で、次に何をするか」を最初に渡す |
| 2 | 今日の記録カード(空)+ 追加フォーム | CTA の着地点 |
| 3 | ヒートマップ | **表示しない**(記録ゼロで52週の空格子を見せない) |
| 4 | 設定とデータ | 初回に用は無いので最下部 |

**規則:**
- 初回画面には **`--signal`(orange)が必ず一点だけ存在する** — それが CTA である。
  「進むべき先が色で示されていない画面」を作らない。
- CTA を押すとフォームへ移動し、**習慣名の入力欄にフォーカスが入る**。
  押した直後にキーボードで打ち始められる状態を作る(押してから探させない)。
- 空状態の文面は勧誘でなく **抑制**する:「欲張らず、まずは1〜3個から」。
  習慣アプリの最大の失敗は初日に10個登録して3日で全部やめることだからである。
- プライバシーは初回に明示する:「データはこの端末のブラウザにだけ保存されます」。

**実装の確認:** ✅ 満たす。`#empty-state` が `#today-section` より DOM 上前に置かれ、
`#btn-start`(`.btn.primary` = `--signal`)が CTA。押下で `#f-name` にフォーカス。
`renderEmptyState()` が習慣0件のとき `#heatmap-section` を `hidden` にする(ac-test AC-27 で検証済)。

### 1-2. 習慣を追加する

**あるべき体験:** 1画面・1フォーム・スクロールなしで終わる。

- 最小入力は **名前だけ**。色は既定値(Signal Orange)、頻度は既定「毎日」で成立する。
- 頻度を「曜日指定」に変えたときだけ曜日チップが現れ、「週N回」のときだけ回数欄が現れる。
  **使わない入力欄を常時見せない**(初見の認知負荷は入力欄の数に比例する)。
- 追加した瞬間、その習慣は **今日の記録の一覧に現れ、押せる状態になる**。
  「追加したのに今日の欄に出てこない」は起こしてはならない(対象曜日でない場合を除く)。
- 6個を超えたら忠告を出す。24個で拒否する。**拒否は理由と次の行動を添えて言う。**

**実装の確認:** ✅ 満たす。`syncFormMode()` が頻度に応じて `#f-days-box` / `#f-times-box` を出し分け。
上限は `MAX_HABITS=24` / `HINT_HABITS=6`(AC-28)。

### 1-3. 毎日のチェック(主動線)

**あるべき体験:** 開く → 行を押す → 終わり。**中間ステップ・確認ダイアログ・保存ボタンは無い。**

- 押す的は **行全体**(丸だけではない)。指でも狙える面積を的にする。
- 未達成の丸は **「空の器」に見えなければならない**。
  枠が背景に溶けて「何も無い」に見えるなら、やることが残っていることを伝えられていない。
  → 未達成の丸の枠は **対背景 3:1 以上**(WCAG 1.4.11)を必須とする。
- 達成した行だけが `--signal` を帯びる。**画面上の orange の量 = 今日の進捗**という符号化を守る。
- 記録は自動保存。保存の成否をユーザーに気にさせない。
  ただし **保存できない環境(localStorage 不可)では黙らない** — 警告帯を出し、
  エクスポートを促す。

**実装の確認:** ✅ 満たす。`.row-main` 全体が `button`(`aria-pressed`)、1クリックで `done`(AC-22)。
`.check` の枠を `--fg-faint` に変更し light 3.77:1 / dark 4.86:1 を確保(旧 `--line` は 1.19:1 だった)。
保存は `SAVE_DEBOUNCE_MS` でデバウンス(AC-30)、不可環境は `#storage-warning`。

### 1-4. 30日後の振り返り

**あるべき体験:** 開いた瞬間、**今**が見えている。

- ヒートマップは **右端(=今日側)を映して開く**。最も関心の低い1年前を既定表示にしない。
- 数字は文脈とともに置く:現在ストリーク / 最長ストリーク / 達成率が **同じ画面に併置**される。
  「現在16日」だけでは、それが自己ベストなのか凡庸なのか分からない。
- セルにホバー/タップ/フォーカスすると、その日が何だったかを言葉で返す(日付・状態)。
  色は概観のためにあり、**個別の日の真実はテキストで確定させる**。
- 「まとめ」と「習慣別」を切り替えられる。まとめモードのセルは押しても記録が変わらないので、
  **押せるふりをしない**(`aria-disabled`)。
- 濃淡は分位点で決める。線形正規化にしない — 記録が少ない時期に全部薄くなり、
  「続けている」という事実が見えなくなるからである。

**実装の確認:** ✅ 満たす。起動時に `.hm-scroll` の `scrollLeft` を右端へ寄せる。
`quantileThresholds()` による分位点5段階(AC-08)、統計併置(AC-21)、
まとめモードは `aria-disabled`、ツールチップは hover/tap/focus の全経路(AC-26)。

### 1-5. 過去を直す / 休んだ日を記録する

- セルは **done → skip → not-done** に巡回する。「消す」ためだけの別UIを作らない。
- **skip(休息)はストリークを断ち切らない**し、達成率の分母からも外れる。
  病気や休養で連続記録が0に戻る設計は、続ける意思そのものを折る。

**実装の確認:** ✅ 満たす(AC-20 / AC-23)。

## 2. 画面状態の設計

### 2-1. 空(初回 / 全習慣削除後)

- 見せる: 空状態カード(説明 + 一次CTA)、追加フォーム、設定
- **隠す**: ヒートマップ節ごと
- 禁止: 記録ゼロの52週グリッド、「0日」「0%」だけが並ぶ統計、ローディング風の灰色ブロック
- 文面は「失敗」ではなく「これから」の語彙で書く

### 2-2. データ有り(通常)

- 上から: 今日の記録 → 追加フォーム → ヒートマップ → 設定
- **今日対象でない習慣は今日の一覧に出さない**(週3回の習慣が毎日出ていると、
  押していないことが罪悪感に化ける)。管理はいつでも設定節から可能。
- 各行に名前・現在ストリーク・最長・達成率。名前は `overflow-wrap: anywhere` で折り、
  長い名前でも行を破壊しない。

### 2-3. エラー / 劣化状態

| 状況 | 見せ方 | 原則 |
|---|---|---|
| localStorage 不可 | 画面上部に警告帯(`--warn-*`)+ エクスポート誘導 | 黙って忘れない |
| インポートJSONが不正 | 通知に理由を出し、**既存データは一切変えない** | 壊れた入力で壊れたデータを作らない |
| 保存データが破損 | 起動時に通知、可能な範囲で正規化して起動 | 白画面で終わらせない |
| 上限超過の追加 | 通知で理由と上限値 | 拒否は必ず理由付き |

通知はページ上部の `role="status" aria-live="polite"` に出す。
**操作したら前の通知は消える** — 役目を終えたメッセージを残さない。

**実装の確認:** ✅ 満たす。`commit()` が `state.ui.notice = null` を行う(M-9修正)。
不正JSONで既存データ不変(AC-24)。

### 2-4. 高密度(習慣が多い)

- 6個を超えたら **忠告する**。「多い」ことを黙認しない。
- 24個で追加を拒否する。無限に増やせる習慣トラッカーは実質使えない。
- 行は縦に積み、1行の高さは変えない。習慣が増えても **1行あたりの走査コストを一定に保つ**。
- ヒートマップは常に1習慣分(またはまとめ)のみ。習慣ごとに24枚のヒートマップを並べない。

## 3. 操作規則

### 3-1. キーボード

| 対象 | キー | 動作 |
|---|---|---|
| 全体 | `Tab` / `Shift+Tab` | 論理順で移動。**フォーカスリングは必ず見える**(`--focus` 2px、対地3:1以上) |
| 今日の行 | `Enter` / `Space` | 記録をトグル(`button` の既定挙動) |
| ヒートマップ | `Tab` | グリッド全体で **1回**(52×7=364個をタブで踏まされない = roving tabindex) |
| ヒートマップ | `←` `↑` | 1日前へ |
| ヒートマップ | `→` `↓` | 1日後へ |
| ヒートマップ | `PageUp` / `PageDown` | 1週(7日)単位で移動 |
| ヒートマップ | `Home` / `End` | **その曜日の行内**で先頭週 / 最終週へ |
| ヒートマップ | `Ctrl+Home` / `Ctrl+End` | グリッド全体の先頭 / 最終選択可能セルへ |
| 曜日チップ | `Space` | チェック切替(`:focus-within` でリング表示) |

**規則:**
- 未来日のセルはフォーカスも操作も受けない(`disabled`)。存在しない日を選ばせない。
- キーボードでセルにフォーカスした時も **ツールチップが出る**。
  マウス利用者だけが日付を知れる状態を作らない。
- グリッドに `role="grid"` を名乗らない。row を持たない構造で grid を名乗るのは
  支援技術への虚偽である。素の `button` の集合として正直に見せる。

**実装の確認:** ✅ 満たす。`onGridKeydown()` に上記全キー、`applyRovingTabindex()`(AC-12)、
`focusin` でツールチップ表示、親は `role="group"`(I-8修正)。

### 3-2. ポインタ / タッチ

- **すべての操作対象は最低 24×24 CSS px の当たり判定を持つ**(WCAG 2.5.8)。
  ヒートマップのセルは日付格子の走査性のため見た目 13px を保つが、
  **当たり判定だけを `::after { inset: -6px }` で 25px に広げる**。
  見た目の密度と指の物理サイズは別問題であり、前者のために後者を犠牲にしない。
- タップでもツールチップが出る(ホバーの無い端末を二級市民にしない)。
- 押下フィードバックは `scale(.995)` の圧縮のみ。色を跳ねさせない。

**実装の確認:** ✅ 満たす。`.hm-cell::after { inset: -6px; z-index: -1 }`。
`z-index: -1` により拡張域はセル本体の背景より後ろに置かれ、
**見えている四角の色 = 押されるセル**という対応が崩れない。

### 3-3. 動きと配慮

- `prefers-reduced-motion: reduce` を尊重し、transition / animation / `scale` 圧縮を無効化する。
  本アプリの動きは 0.15s の色変化のみだが、**「小さいから安全」は前庭障害の利用者には成り立たない**。
- `color-scheme` を宣言し、スクロールバー・`<select>`・カラーピッカーといった
  ブラウザ描画部分もテーマに追従させる。暗い紙面に明色のスクロールバーが1本走る状態を作らない。
- 意味を **色だけに負わせない**(WCAG 1.4.1)。
  ヒートマップの「記録なし」は色の薄さに加え、`--empty-edge` の内枠という**形**でも示す。

**実装の確認:** ✅ 満たす。`@media (prefers-reduced-motion: reduce)` ブロック、
3つのテーマブロックすべてに `color-scheme`、`.hm-cell[data-level="0"]` に `inset` 枠。

## 4. 狭い画面での振る舞い

**方針: 折り返して収める。横スクロールを本文に持ち込まない。**

| 要素 | 狭い画面(≤520px)での振る舞い |
|---|---|
| ページ全体 | `body` に横スクロールを与えない。パディングを 14px/10px に詰める |
| 今日の行 | 縦積みのまま。丸・名前・統計が折り返して収まる |
| 追加フォーム | `flex-wrap` で複数行に折り返す。ラベルと入力が離れない |
| 曜日チップ | 折り返して2段になる。潰して読めなくしない |
| ヒートマップ | **ここだけ横スクロール**。`.hm-scroll` の内側に封じ込め、ページ本体は動かさない |
| ヒートマップのセル | 12px に縮小。ただし **当たり判定は `::after` により 24px を維持** |
| ツールチップ | 画面端で反転・クランプし、6px 以上の余白を保って画面外に出ない |

**規則:**
- 狭い画面でも **主動線(今日の丸を押す)がスクロールなしで到達できる**こと。
  今日の記録は常に画面最上部の実質コンテンツである。
- ヒートマップは「読めなくてよい」情報ではないが、**狭い画面での優先度は主動線より下**。
  横スクロールを許容するのはここだけ。

**実装の確認:** ⚠️ 部分的に未確認。
CSS 上は `@media (max-width: 520px)` で `--cell: 12px` とパディング調整、
`.hm-scroll { overflow-x: auto }` によるスクロール封じ込め、`body` に `overflow-x` 無しを
ac-test(AC-25)が静的に検証している。ツールチップのクランプも `showTooltip()` に実装がある。
ただし **380px 実機での目視は本フェーズでも行っていない**(ux-review.md の未確認3通は未解消)。
レイアウトエンジンを持たない検証環境のため、これは「CSS構造上そうなるはず」であって
「見て確かめた」ではない。再レビュー時に必ず実機で確認すること。

## 5. 意図的に採らなかった選択

| 案 | 却下理由 |
|---|---|
| 削除に確認ダイアログを出す | 主動線を守るため、確認は破壊操作(習慣削除)のみに限る。日々のトグルには一切挟まない |
| 通知・リマインダー | 依存ゼロ・単一HTMLの制約下では実現できず、中途半端な実装は「来なかった通知」への信頼喪失を生む |
| 習慣ごとにヒートマップを並べる | 24枚のヒートマップは概観ではなく壁紙になる。切替式を選ぶ |
| 達成率だけを大きく出す | 率は「今日押す」動機にならない。ストリークと併置してこそ意味を持つ |
| 広い画面(940px超)で行を2カラム化 | `max-width: 940px` は機能不変の制約として据置。行内の間延び(ux-review F-9)は後追い課題として残す |
