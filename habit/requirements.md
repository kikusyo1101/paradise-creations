# 習慣トラッカー — specify フェーズ 要件定義 (requirements.md)

- **wish**: 「毎日の習慣を記録し、連続日数とヒートマップで可視化する習慣トラッカー」
- **成果物**: 単一 HTML ファイルの Web アプリ(依存ゼロ・ビルド不要・オフライン動作・localStorage 永続化)
- **担当**: priest (要件定義)
- **作成日**: 2026-08-31
- **唯一の根拠**: `findings.md` (discover フェーズ調査報告)。本書の全要件は findings.md の記述に紐づく。findings.md に無い根拠は記載しない。

---

## 1. 目的とスコープ

### 1-1. 目的

findings.md §2 の結論に従い、本アプリは「記録アプリ」ではなく
**「続けている自分を見せて、途切れても戻ってこられる装置」** として作る。

達成すべき価値は3つ:

1. **摩擦ゼロの記録** — 開いて1タップで終わる。記録の手間が習慣の手間を超えた瞬間に離脱する(findings §2, §5-5: ヘルスアプリ利用者の約70%が10回使用で離脱)。
2. **途切れても壊れない可視化** — ストリークを主役にしつつ唯一の指標にしない。密度・最長記録・skip を併置する(findings §5-1, §7-1: UCL 研究「ストリークが途切れるとアプリと行動の両方を放棄」)。
3. **自分のデータが自分の手元にある** — アカウント不要・完全オフライン・エクスポート可能(findings §2 暗黙ニーズ, §3 M9/M10)。

### 1-2. スコープ (in scope)

- 習慣の CRUD、今日の一覧、ワンタップ記録
- 現在/最長ストリーク、直近30日の密度指標
- GitHub 型ヒートマップ(全習慣まとめ + 習慣個別)
- 過去日の遡り記録・修正
- done / not-done / skip の3状態
- 頻度設定(毎日 / 特定曜日 / 週N回)
- 週開始曜日の設定
- localStorage 永続化(安全ラッパ経由) + JSON エクスポート/インポート
- ダークモード(システム配色追従)
- キーボード操作・スクリーンリーダー対応

### 1-3. 非スコープ (out of scope)

findings.md が明確に「リスク」「nice-to-have」「規模的に不要」と位置づけたもの:

| 非スコープ項目 | 除外理由 (findings 根拠) |
|---|---|
| アカウント登録・クラウド同期・サーバ通信 | §2「自分のデータが自分の手元にあること」。Loop の中核価値 = オフライン動作 |
| 罰・ペナルティ設計(HP 減少、キャラクター死亡) | §5-3「奮い立つ人もいれば、そうでない人もいる」。汎用ツールでのデフォルト ON はリスク |
| プッシュ通知・リマインダー | §5-6「受動攻撃的な通知は離脱要因」 |
| ゲーミフィケーション(レベル、報酬、ガチャ) | §5-3 と同根。§5-7「データ過多は苛立ちを増やす」 |
| IndexedDB / 外部 DB | §6-2「本件の規模では localStorage で完全に妥当」 |
| フレームワーク・外部 CSS/JS/フォントの読み込み | §6-4「ビルド不要 = 素の HTML + style + script」「フォントも外部読み込みせずシステムフォントスタック」 |
| 数値型/時間型の習慣、メモ機能、PWA 化、月区切り表示モード、祝福アニメーション、並べ替え/アーカイブ、週次振り返りサマリ、アイデンティティ強化文言 | §4 nice-to-have。初版では実装しない(§5-7 初期画面は簡潔に) |
| 部分描画の最適化・仮想スクロール | §6-3「365〜371 セルなら性能上の心配は不要。過剰設計しないこと」 |
| 複数タブ間のリアルタイム同期 | §6-2「余裕があれば対応する」= 必須ではない |

## 2. 機能要件 (FR)

各要件に findings.md の根拠を明記する。

### FR-01 習慣の追加/編集/削除
習慣は「名前」「色」を必須属性として持ち、追加・編集・削除ができる。削除は確認を挟む。
**根拠**: §3 M1(全事例に存在する最小単位。Habitica「色分けされたタスクとストリークカウンタで一目で状況が分かる」)。

### FR-02 習慣数のソフト上限とガイド
習慣数が推奨上限(4〜6個)を超えたとき、UI 上に控えめな注意ヒントを表示する。追加自体はブロックしないが、上限(24個)を超える追加は拒否する。
**根拠**: §5-4「12個追跡すれば3週目には8個を無視することが保証される」「1〜3個から始めることを研究が推奨」、§4「習慣数のソフト上限とアラート(4〜6個)」、§1-2 Streaks はタスク数を24に固定。

### FR-03 今日の一覧とワンタップ記録
起動直後の初期画面に「今日やる習慣」の一覧を表示し、各行を1回タップ/クリックするだけで done を記録・解除できる。モーダル・カテゴリ選択・保存ボタンなどの中間ステップを挟まない。
**根拠**: §3 M2、§5-5「モーダル→カテゴリ選択→保存、のようなフローは死。1タップ」、§1-6 スコアカード第1項目「ワンタップ記録(摩擦ゼロ)」。

### FR-04 3状態モデル (done / not-done / skip)
各(習慣, 日付)の記録は `done` / `not-done` / `skip` の3値を取る。`skip` は「病気」「旅行」「対象日でない」を表し、ストリークを断絶させず、達成率の分母からも除外する。
**根拠**: §3 M7(Loop v2.1 で skip 追加)、§5-2「二値しかない状態設計は病気/旅行/対象外を全部『失敗』に潰す」、§1-6「赦しの仕組み(skip パス)」がスコアカード必須項目。

### FR-05 頻度設定
習慣ごとに「毎日」「特定曜日(曜日の複数選択)」「週N回」を設定できる。対象日でない日はストリーク計算・達成率の分母から除外し、ヒートマップ上でも未達と区別して表示する。
**根拠**: §3 M8、§1-2 Streaks「毎日やるべきでないタスクもある。曜日を設定してストリークを壊さないようにする」「これがないと週3の運動が常に"失敗"に見える」。

### FR-06 現在ストリークと最長ストリークの併置表示
習慣ごとに「現在の連続日数」と「過去最長の連続日数」の両方を表示する。
**根拠**: §3 M3、§1-6「現在のストリーク + 最長ストリーク の両方を出すとレバレッジが増す」。

### FR-07 ストリークに依存しない第二指標(密度)
習慣ごとに「直近30日の達成率(X/30 形式および百分率)」を表示する。skip と対象外日は分母から除外する。この指標はストリークが0になっても値を保つ。
**根拠**: §3 M11(Loop の habit score の思想)、§1-6「ヒートマップは連続を気にしない——時間あたりの密度を評価する」「90日で70日やって4回の空白がある人の方が長期的成果は上」、§5-1「ストリークを唯一の指標にしてはいけない」、§7-1。

### FR-08 GitHub 型ヒートマップ
52〜53列 × 7行のグリッドを描画する。列=週、行=曜日。月ラベルを上、曜日ラベルを左に置き、凡例を添える。
**根拠**: §3 M4(wish の明示要求)、§1-4「レイアウトは 52〜53列 × 7行。列=週、行=曜日。月ラベルを上、曜日ラベルを左」。

### FR-09 ヒートマップの離散5段階配色
セルの色は連続グラデーションではなく level 0〜4 の離散5段階で表現する。level は線形スケールではなく、ドメインに合わせた固定閾値(または分位点ビニング)で決定する。level 0(カウント0)は透明にせず最も薄い色を使う。
**根拠**: §1-4「色は連続グラデーションではなく 4〜5 段階の離散レベル。GitHub は 0 を含む5段階」「線形スケールは誤り。分位点ビニングまたは固定閾値」、§5-11、§5-14「カウント0を透明にするとグリッド形状が崩れる」。

### FR-10 全体ヒートマップと習慣別ヒートマップ
「全習慣を合算したヒートマップ」と「習慣を1つ選んだときの個別ヒートマップ」の両方を提供する。
**根拠**: §3 M5「Loop・HabitHeat・Daisy テンプレートいずれも習慣詳細画面にカレンダーヒートマップを持つ」。

### FR-11 過去日の遡り記録/修正
ヒートマップのセルをクリック/タップすると、その(習慣, 日付)の状態を done → skip → not-done の順に巡回トグルできる。未来日はトグル不可。
**根拠**: §3 M6「記録忘れは必ず発生する。修正できないと記録の信頼性が崩れ、以後使われなくなる」。

### FR-12 未来日の扱い
今日より後の日付のセルはミュート表示にし、操作対象にしない(またはそもそも描画しない)。
**根拠**: §1-4「未来日は空/ミュート表示、またはそもそも描画しない」、§5-13。

### FR-13 セルのツールチップ(hover と tap の両経路)
セルにポインタを乗せたとき、およびタッチデバイスでタップしたときに、「日付 + 曜日 + 状態(件数)」のツールチップを表示する。hover のみの実装は禁止。
**根拠**: §1-4「ホバーがないので tap-to-show tooltip」、§5-16「タッチデバイスに hover ツールチップだけ用意する」が落とし穴として明示。

### FR-14 週開始曜日の設定
設定で週の開始曜日(日曜 / 月曜)を選べる。この設定値はヒートマップの「行の曜日順」と「開始日の巻き戻し計算」の両方に適用される。
**根拠**: §4「週の開始曜日の設定 — §5 のバグを踏まえると『準 must』に近い」、§6-1「週の開始曜日は設定値として持ち、ヒートマップの行順・巻き戻し計算の両方に使う」、§1-5 Habit Heatmap の実バグ「全部1日ずれている」→ v1.4 で「週の開始曜日設定に動的に適応」する修正。

### FR-15 開始日の巻き戻し
ヒートマップの描画開始日は、範囲の開始日から「直前の週開始曜日」まで巻き戻した日付とする。先頭列が欠けた週にならないようにする。
**根拠**: §1-4「開始日は直前の日曜(または月曜)まで巻き戻す」、§5-10「先頭列の巻き戻し忘れ」。

### FR-16 localStorage への自動永続化と起動時復元
状態変更時に自動保存し、起動時に復元する。アカウント登録・ネットワーク通信は一切行わない。
**根拠**: §3 M9、§2 暗黙ニーズ「アカウント登録・サインアップ・クラウド同期を挟まないこと」。

### FR-17 ストレージ安全ラッパ
localStorage へのアクセスは以下を備えた単一のラッパ関数経由でのみ行う。
- 利用可能性の feature detection(MDN の `storageAvailable()` パターン)
- 書き込みの try/catch による `QuotaExceededError` / `NS_ERROR_DOM_QUOTA_REACHED` 捕捉
- 読み込みの try/catch による `SyntaxError` 捕捉とデフォルト値フォールバック
- 破損データを破棄する前に別キーへ退避
- `setItem`/`getItem` のみ使用(プロパティアクセス禁止)
- 保存は `JSON.stringify`、読み込みは `JSON.parse`
**根拠**: §6-2 全項目(MDN: 「プライベートブラウジングでは quota 0 の空の localStorage を返すことがある」「ネイティブメソッドとの衝突、プロトタイプ汚染を避けるため setItem/getItem を使う」、§6-2「壊れた生データは別キーに退避してから上書きする」)。

### FR-18 ストレージ利用不可時のフォールバックと明示
localStorage が使えない場合(Safari プライベートブラウジング 14未満は全 `setItem` が throw、`file://` オリジンでの挙動差など)、メモリ上の状態にフォールバックして動作を継続し、「この変更はこのセッションでのみ保持されます」という警告を UI に明示する。
**根拠**: §6-2「書けない場合はメモリにフォールバックし、『この変更はこのセッションでのみ保持されます』と明示する」、§6-4「`file://` でストレージが使えないケースを feature detection で検出して警告を出す」。

### FR-19 バージョン付きエンベロープとマイグレーション
保存形式は `{ v: 1, habits: [...], logs: {...} }` のバージョン付きエンベロープとし、読み込み時に `v` を見て変換する経路を初版から持つ。保存キーは名前空間付きの単一キー(例 `paradise.habit.v1`)。
**根拠**: §6-2「スキーマバージョニングとマイグレーションを最初から入れる」「キーは名前空間付きの単一キーにまとめる。複数キーに散らすと部分書き込みで不整合が起きる」。

### FR-20 書き込みのデバウンス
起動時に1回読み込んでメモリ上の状態を正とし、localStorage への書き込みはデバウンスする(操作ごと・キーストロークごとに書かない)。
**根拠**: §6-2「同期 API でメインスレッドをブロックする。中位の Android で 2MB 読み込み時に 80〜120ms のブロック」「起動時に1回読んでメモリ上の状態を正とし、書き込みはデバウンスする」。

### FR-21 JSON エクスポート / インポート
全データを JSON ファイルとしてダウンロードでき、ファイル選択で読み戻せる。`Blob` + `URL.createObjectURL` と `<input type="file">` + `FileReader` で外部依存なしに実装する。インポート時は形式検証を行い、不正なら現在のデータを破壊しない。
**根拠**: §3 M10「localStorage はユーザーがブラウザを掃除すると消える。データ消失はこの手のアプリで最も致命的な裏切り」、§6-4「localStorage がユーザーのブラウザ掃除で消える以上、これは保険ではなく必須機能」、§7-5。

### FR-22 ダークモード / システム配色追従
`prefers-color-scheme` に追従し、手動切り替えも可能にする。配色は CSS カスタムプロパティで一元管理する。
**根拠**: §3 M12「Loop・Habit Heatmap いずれも明示的な機能として掲げる。夜に開くアプリである」、§6-3「色は CSS カスタムプロパティ + data-level 属性セレクタ。テーマ変更が1箇所で済み、ダークモードも同じ仕組みで切り替わる」。

### FR-23 アクセシビリティ
- 各セルに「日付 + 曜日 + 状態」を含む意味のある `aria-label` を付ける
- グリッドは roving tabindex(フォーカス可能なセルは常に1つ)+ 矢印キー移動
- 色を唯一の情報伝達手段にしない(状態を aria-label とツールチップのテキストに含める)
**根拠**: §3 M13、§1-4「各セルに意味のある aria-label(「2026年1月15日水曜日に5件」)、roving tabindex、矢印キー移動、色だけを情報伝達手段にしない」、§5-12「色覚特性・スクリーンリーダーで壊滅」。

### FR-24 モバイル対応(コンテナ内横スクロール)
ヒートマップは `overflow-x` を持つ専用コンテナ内で横スクロールし、ページ自体を横スクロールさせない。セルは最低 12×12px を確保する。
**根拠**: §1-4「モバイル: 52列が入らないのでコンテナ内で横スクロール(ページ自体を横スクロールさせない)。タッチ標的は最低 12×12px」、§5-15、§6-3「横スクロールは overflow-x を持つ専用コンテナに閉じる」。

### FR-25 空状態の設計
習慣が0件の初回起動時に、真っ白なグリッドを見せず、アプリの目的と「1〜3個から始める」案内を含む親しみやすい空状態を表示する。
**根拠**: §5-8「データ0の初回起動でグリッドが真っ白だと何のアプリか分からない。親しみやすい空状態を出す」、§7-6「初回起動の空状態を設計する(サンプル習慣の提案 or 1〜3個から始める案内)」、§1-6「研究の多くは1〜3個の習慣から始めることを推奨」。

### FR-26 日付キーの単一生成関数と日付境界の再評価
「今日」の日付キー生成は1箇所の関数に集約する。タブを開いたまま日付をまたぐケースに備え、`visibilitychange` イベントで「今日」を再評価して再描画する。
**根拠**: §6-1「『今日』の判定は日付キー生成を1箇所の関数に集約する。日付をまたいだままタブを開きっぱなしにするケースがあるので、visibilitychange で再評価する」。

### FR-27 日付演算の安全な実装
日付キーはローカル日付の `"YYYY-MM-DD"` 文字列を唯一の真実とする。`Date` オブジェクトや UTC の ISO 文字列を保存しない。日付の加算は `new Date(y, m, d + n)` 形式で行い、ミリ秒加算を使わない。
**根拠**: §6-1「日付キーはローカル日付の "YYYY-MM-DD" 文字列を正とする。`toISOString()` は UTC 変換するので、JST では日付が1日前にずれる(23:00 に記録すると前日になる)」「日付の加算は new Date(y, m, d + n) 形式。ミリ秒の +86400000 は DST で壊れる」、§5-17、§7-2。

## 3. 非機能要件 (NFR)

### NFR-01 依存ゼロ
外部の JS ライブラリ・CSS フレームワーク・Web フォント・アイコン CDN を一切読み込まない。フォントはシステムフォントスタックを使う。
**根拠**: §6-4「ビルド不要 = 素の HTML + `<style>` + `<script>`。フレームワークなし。フォントも外部読み込みせずシステムフォントスタックを使う(オフライン動作のため)」。

### NFR-02 単一ファイル
成果物は 1 つの `.html` ファイルのみ。HTML / CSS / JS がすべてその中にインラインで含まれる。ビルド手順を必要としない。
**根拠**: 前提条件(findings §冒頭「単一 HTML ファイルの Web アプリ (ビルド不要)」)、§6-4。

### NFR-03 完全オフライン動作
ネットワークが無い状態、および `file://` プロトコルで開いた場合でも全機能が動作する。外部への通信を一切行わない。`file://` でストレージが使えない場合は FR-18 の警告経路に落ちる。
**根拠**: §6-4「`file://` で開いても動くこと」、§1-1 Loop「インターネット接続やオンラインアカウント登録を必要としない」。

### NFR-04 ストレージ容量
1オリジンあたり約 5MB(UTF-16 で1文字2バイト、実質 ~250万文字)の制約下で動作する。想定データ量(習慣10個 × 10年)は数百KB程度で十分収まる。超過時は `QuotaExceededError` を捕捉してユーザーに通知し、データを破壊しない。
**根拠**: §6-2「容量は 1オリジンあたり約 5MB」「UTF-16 で1文字2バイト」「習慣10個 × 10年 × 日付キーでも数百KB程度なので十分」「書き込みは必ず try/catch で QuotaExceededError を捕まえる」。

### NFR-05 アクセシビリティ
- 色を唯一の情報伝達手段にしない
- キーボードのみで全機能(記録・トグル・設定・エクスポート)を操作できる
- ヒートマップグリッドは roving tabindex + 矢印キー移動
- 全セルに日付と状態を含む `aria-label`
**根拠**: §3 M13、§1-4、§5-12。

### NFR-06 性能
- ヒートマップ 365〜371 セルの描画に過剰な最適化を持ち込まない(単一 state → `render()` の一方向)
- 起動時の localStorage 読み込みは1回のみ、書き込みはデバウンス
- メインスレッドを長時間ブロックしない
**根拠**: §6-3「365〜371 セルなら性能上の心配は不要。過剰設計しないこと」、§6-4「状態 → 描画は単一の state オブジェクト → render() を呼ぶだけの一方向にする。部分更新の最適化は 365 セル規模では不要」、§6-2 の同期 API ブロック(80〜120ms)への対処。

### NFR-07 データ安全性
- 秘密情報を localStorage に保存しない
- 破損データは捨てる前に退避キーへ保存する
- インポート失敗時に既存データを破壊しない
**根拠**: §6-2「秘密情報は絶対に置かない。同一オリジンの任意スクリプトから読める」「壊れた生データは別キーに退避してから上書きする(いきなり捨てない)」。

### NFR-08 実装方式(ヒートマップ)
CSS Grid の `grid-template-rows: repeat(7, <cell>)` + `grid-auto-flow: column` を用い、日付順にセルを append するだけで週=列に自動整列させる。JS 側で行/列の計算を行わない。色は CSS カスタムプロパティ + `data-level="0..4"` 属性セレクタで指定する。
**根拠**: §6-3「依存なしの CSS Grid 実装が確立済み。JS 側の行列計算が不要になる」「色は CSS カスタムプロパティ + data-level 属性セレクタ」、§1-4。
