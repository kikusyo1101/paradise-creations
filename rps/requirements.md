# 要件定義書（Requirements）— じゃんけんゲーム（対コンピュータ）

本書は specify フェーズの成果物であり、`findings.md`（discover フェーズ）を入力として、**何を・なぜ**作るかを定義する。実装方法（どう作るか）は含めない。次フェーズ（設計・実装）への入力となる。

---

## 1. 意図（Intent）

- **目的**: ブラウザだけで即座に遊べる、対コンピュータのじゃんけんゲームを提供する。
- **価値の中心**: `findings.md` §1 が示す「**摩擦ゼロの即応性**」と「**勝敗の明快さ**」。ログイン・ロード・チュートリアルなしに、開いた瞬間に1回目を遊べること。
- **体験ゴール**:
  - 自分の手・相手の手・勝敗が一目で分かる、明快で気持ちの良いフィードバック。
  - スコアが積み上がり「もう1回」を押したくなる反復ループ。
  - コンピュータが後出し（ズル）をしていないと信じられる公平さ。
  - スマホのタップでもPCのクリック／キーボードでも遊べる。
- **成功の定義**: 1画面で完結し、`findings.md` の 🔴 must-have と 🟠 high をすべて満たすこと。

---

## 2. ユーザーストーリー（User Stories）

- **US-1**: 遊び手として、開いてすぐグー／チョキ／パーのどれかを選びたい。すぐ遊びたいから。
- **US-2**: 遊び手として、コンピュータが何を出したかを毎回見たい。結果に納得したいから。
- **US-3**: 遊び手として、勝ったか負けたかあいこかを一目で知りたい。結果をすぐ理解したいから。
- **US-4**: 遊び手として、自分の手と相手の手を並べて確認したい。「なぜその結果か」を瞬時に理解したいから。
- **US-5**: 遊び手として、これまでの勝ち・負け・あいこの累計を見たい。積み上がる達成感が欲しいから。
- **US-6**: 遊び手として、続けて何度でも遊びたい。1回で終わらせたくないから。
- **US-7**: 遊び手として、スコアをリセットして最初からやり直したい。区切りをつけたいから。
- **US-8**: 遊び手として、クリック／タップだけでなくキーボードでも手を選びたい。手元の入力手段で遊びたいから。
- **US-9**: 遊び手として、コンピュータが後出ししていないと感じたい。公平に勝負したいから。

---

## 3. 機能要件（Functional Requirements）

`findings.md` §4 のスコープに準拠。🔴 = must-have、🟠 = high。

- **FR-1 🔴 手の選択**: プレイヤーはグー／チョキ／パーの3択から1つを選べる（クリック／タップ）。
- **FR-2 🔴 コンピュータの手の決定と表示**: 1ラウンドごとにコンピュータの手を乱数で決定し、画面に表示する。決定はプレイヤーの手に依存せず（後出しをしない）、その手が偏らないこと。
- **FR-3 🔴 勝敗判定**: 標準ルールで勝ち／負け／あいこを判定する。ルールは FR-3a のとおり。
  - **FR-3a 勝敗ルール**: グーはチョキに勝つ／チョキはパーに勝つ／パーはグーに勝つ。プレイヤーとコンピュータが同じ手なら「あいこ」。
- **FR-4 🔴 結果の表示**: 判定結果を明確なテキスト（WIN／LOSE／DRAW 等）で提示し、結果に応じた視覚的区別（色など）を与える。
- **FR-5 🔴 手の対比表示**: そのラウンドのプレイヤーの手とコンピュータの手を、両方分かる形で同時に表示する。
- **FR-6 🟠 スコア追跡**: 複数ラウンドにわたり、プレイヤーの勝ち数・負け数（＝コンピュータの勝ち数）・あいこ数を累積し、画面に常時表示する。
- **FR-7 🟠 もう一度 / 次ラウンド**: 1ラウンドの結果表示後、次のラウンドを開始して続けて遊べる。
- **FR-8 🟠 リセット**: スコア（勝ち・負け・あいこ）をゼロにクリアできる導線を用意する。
- **FR-9 🟠 明確な視覚フィードバック**: 選択した手のハイライト、結果に応じた色／強調など、状態が視覚的に分かる。
- **FR-10 🟠 キーボード入力**: クリック／タップに加え、キーボードでも手を選べる（例: R/P/S または 1/2/3）。
- **FR-11 摩擦ゼロの起動**: ページを開いた直後に、追加操作なしで1ラウンド目を遊べる状態であること（ログイン・チュートリアル・待機ロードなし）。

---

## 4. 受け入れ基準（Acceptance Criteria）

各基準はチェック可能。🔴/🟠 は対応する must-have/high を示す。

- **AC-1 🔴（FR-1）**: 画面上でグー・チョキ・パーそれぞれを選べる操作要素が存在し、いずれかを選択すると1ラウンドが実行される。
- **AC-2 🔴（FR-2）**: 各ラウンドでコンピュータの手が表示される。コンピュータの手はプレイヤーの選択後に決まるのではなく乱数で独立に決まり、多数回の試行でグー・チョキ・パーの3手がいずれも出現する（特定の1手に固定されない）。
- **AC-3 🔴（FR-2）**: コンピュータの手は、プレイヤーが選んだ手に有利になるよう選ばれない（プレイヤーの手を見て後出しで勝ちを狙わない）。
- **AC-4 🔴（FR-3a・勝ちルール）**: プレイヤー=グー かつ コンピュータ=チョキ のとき結果は **WIN（プレイヤーの勝ち）**。
- **AC-5 🔴（FR-3a・勝ちルール）**: プレイヤー=チョキ かつ コンピュータ=パー のとき結果は **WIN**。
- **AC-6 🔴（FR-3a・勝ちルール）**: プレイヤー=パー かつ コンピュータ=グー のとき結果は **WIN**。
- **AC-7 🔴（FR-3a・負けルール）**: プレイヤー=チョキ かつ コンピュータ=グー のとき結果は **LOSE**。
- **AC-8 🔴（FR-3a・負けルール）**: プレイヤー=パー かつ コンピュータ=チョキ のとき結果は **LOSE**。
- **AC-9 🔴（FR-3a・負けルール）**: プレイヤー=グー かつ コンピュータ=パー のとき結果は **LOSE**。
- **AC-10 🔴（FR-3a・あいこ）**: プレイヤーとコンピュータが同じ手（グー=グー／チョキ=チョキ／パー=パー）のとき結果は **DRAW（あいこ）**。上記 AC-4〜AC-10 で全9通りの手の組み合わせが網羅され、いずれも一意の結果になる。
- **AC-11 🔴（FR-4）**: 各ラウンド後、WIN／LOSE／DRAW のいずれかが明確なテキストで表示され、結果ごとに視覚的な区別（色など）がある。
- **AC-12 🔴（FR-5）**: 各ラウンドで、プレイヤーの手とコンピュータの手が両方同時に確認できる形で表示される。
- **AC-13 🟠（FR-6）**: 画面にプレイヤーの累積勝ち数・負け数・あいこ数が表示される。
- **AC-14 🟠（FR-6）**: プレイヤーが勝つと勝ち数が1増える。負けると負け数が1増える。あいこだとあいこ数が1増える。該当しないカウンタは変化しない。
- **AC-15 🟠（FR-7）**: ラウンド結果の表示後、追加操作で次のラウンドを開始でき、スコアは累積として引き継がれる。
- **AC-16 🟠（FR-8）**: リセット操作を行うと、勝ち・負け・あいこの各カウンタが 0 に戻る。
- **AC-17 🟠（FR-9）**: プレイヤーが選択した手が視覚的にハイライト／識別できる。
- **AC-18 🟠（FR-10）**: 定義されたキーボードキー（例: R/P/S または 1/2/3）でグー・チョキ・パーをそれぞれ選択でき、クリック／タップと同じくラウンドが実行される。
- **AC-19（FR-11）**: 初回表示時、追加のログイン・チュートリアル・明示的ロード操作なしに、すぐ手を選んで遊べる。
- **AC-20（NON-GOALS）**: ゲームはネットワーク通信・サーバ・外部APIを必要とせず、静的に開いた状態で全機能が動作する。

---

## 5. 非目標（NON-GOALS）

`findings.md` §4 に準拠。v1 では以下を行わない：

- **マルチプレイヤー / 対人対戦**（オンライン・ローカルを問わず）。
- **アカウント / ログイン / プロフィール**。
- **ネットワーク通信 / サーバ / データベース / 外部API**（クライアント完結・静的配信で動作する）。
- **ランキング / リーダーボード / SNS共有**。
- **課金・広告・アナリティクス**。

---

## 6. 任意（Optional — 余力があれば、v1 の必須ではない）

`findings.md` §4 の 🟡。受け入れ基準の対象外：

- Best-of-N（例: 5本勝負）、簡単なアニメーション、選択履歴の表示、ミュート可能な効果音、スコアの永続化（localStorage）。
