## 1. 総評(出荷可否の意見とその根拠)

### 意見: **条件付きで出荷不可。BLOCKER 1件の修正を出荷の前提とする。**

計算コア(L1)は、設計文書が要求した規律を**驚くほど忠実に守っている**。契約 C-1〜C-7 は7項目すべて実測で合格し、EPS は design §5-4 が列挙した箇所に過不足なく置かれ、`tippingPoint` の判定順序(D-7)は仕様通りで、`reweight` と `tippingPoint` の写像一致(AC-10 の核心)は 8,594 行の実行可能ケースで**残差 7.2e-16 / 違反 0 件**だった。純粋性も実測で確認できた。**コア単体で見れば、これは出荷できる品質にある。**

問題は**コアの外**にある。

**BLOCKER-1** — レンダリング層(L2)の `index.html:2180` が、`g_j > 1` という **EPS 抜きの境界比較**で「この基準は単独で結論をひっくり返せる」と判定している。これは design §5-4 が「`===` による 0 との比較を1箇所も書かない」と定めた規律の対象そのものであり、L1 が EPS で正しく吸収している境界を、L2 が最下位ビットで踏み抜く。結果として **同一画面の Z3 と Z4 が正面から矛盾する**:Z3 が「基準1 — 逆転不能」と書いている隣で、Z4 が「基準1 は単独で結論をひっくり返せます」と書く。

これは表示上の瑕疵ではない。**本製品の一次出力は「この結論はどれくらい壊れやすいか」であり、その判断そのものが自己矛盾する。** ユーザーは画面の2箇所から反対の助言を受け取る。しかも `d_k = 0` になる基準(= 2つの選択肢がその基準で並ぶ)は現実の比較で普通に起き、全数探索で**有効入力の 8.21%** で発生した。テストは `winContrib` の値と `criticality` の値を**別々に**検証しているため、この矛盾を構造的に見ることができない。AC-12 が「相互整合を検証する価値がある」と明記していた、まさにその整合が破れている。

**MAJOR は3件。** ①`normalizeWeights` が Σŵ の overflow で事後条件を破り、画面に「重み 0.0% / スコア 0.0」という嘘の数字を出す。②`fmt.*` の「最後の砦」に穴があり、文字列 `"Infinity"` が画面に出る到達経路が実在する(design §5-6 D-10 の「1本も残さない」への反例)。③同点(tie)なのにグリッドで1行だけが勝者としてハイライトされる。①②は localStorage 経由でのみ到達するが、design §3-6 が「DevTools での書き換え」を明示的に想定した経路であり、かつ §8-5 が「本製品で最も危険な故障モード」と呼んだ NaN 遮断と同じ性質の穴である。

**出荷条件:** BLOCKER-1 を修正すること。MAJOR-1〜3 は同時修正が望ましい(いずれも数行)。MINOR は次回に回してよい。

**なお、本レビューで取り下げた指摘を明記しておく。** 「`reweight` が x を [0,1] にクランプしない」「`analyze` の catch-all」「`weightsBroken` 経路の文言」は、実行して**現行の UI からは到達しないことを確認した**ため BLOCKER/MAJOR から降格し、MINOR および §6 に記録した。「§8-10 のちらつき」は再現を試みて**壊れなかったため指摘を取り下げた**。

### BLOCKER-1 — L2 の `g_j > 1` が EPS 抜きの境界比較で、Z3 と Z4 が同一画面で矛盾する

**行番号:** `index.html:2180`(判定)、`index.html:2198-2200`(文言生成)

```js
2180:  if (v > 1) { node.classList.add("crosses"); crossed.push(g.name); }
...
2198:  setText($("g-cross"), crossed.length > 0
2199:    ? "この線を越えた基準は、それ単独で結論をひっくり返せます。→ " + crossed.join("、")
2200:    : "100% の線を越えた基準はありません。");
```

**現象:**

design §3-5 / AC-12 の恒等は `g_k ≤ 1 ⟺ 基準 k は下方向に逆転不能` である。L1 側の `tippingPoint`(`index.html:1034`)はこれを **`down = (wk * dk) > (d0 + EPS)`** と EPS 付きで判定し、境界を正しく「逆転不能」側に倒す。ところが L2 は同じ判定を **`v > 1`** と EPS 抜きで行う。

ある基準で2つの選択肢が並ぶ(`d_k = 0`)と、`D₀ = w_k·d_k` がちょうど成立し、`g_k` は厳密に 1 になる。float ではこれが `1.0000000000000002` に落ちるため、**L1 は「逆転不能」、L2 は「単独で覆せる」と、正反対の結論を同時に表示する。**

これは design §5-4 が「**`===` による 0 との比較を1箇所も書かない。上の11箇所が全てであり、コードレビューはこのリストとの突合で行う**」と定めた規律の、まさに対象である。E-4 が守っている境界を、L2 が素手で触っている。

**再現させた実行出力:**

入力は **すべて UI から実際に打てる値**(整数重み・0.5刻みスコア)である。

```
──────── M-1  L1「逆転不能」 vs L2「単独で覆せる」— 決定的再現 ────────
  試行1: g_基準1 = 1.0000000000000002 (>1: true) / criticality[基準1].infeasible = true
  試行2: g_基準1 = 1.0000000000000002 (>1: true) / criticality[基準1].infeasible = true
  試行3: g_基準1 = 1.0000000000000002 (>1: true) / criticality[基準1].infeasible = true
  入力: 重み 39 / 5、案甲=[6.5, 9.5]、案乙=[4.5, 9.5](すべて UI で打てる値)
  順位: ["案甲=68.4","案乙=50.7"]  D₀=17.7
  厳密値の検算: w1 = 39/44, d1 = (6.5-4.5)/10 = 0.2, D₀ = w1*d1 = 39/44*0.2
    w1*d1 = 0.17727272727272728   D₀(実測) = 0.17727272727272725
    差 w1*d1 − D₀ = 2.776e-17  ← 厳密には 0(境界ちょうど)
  L1 の判定: down = (w·d > D₀+EPS) = false → 逆転不能(正しい。境界は逆転不能側)
  L2 の判定: g = w·d/D₀ = 1.0000000000000002 > 1 = true → 「単独で覆せる」(誤り)
  同一画面に同時に出る2つの文言:
    Z3 行: "基準1 — 逆転不能。案甲 がこの基準でも勝っている(または差が僅少)ため、重みを上げても 案甲 のリードが広がるだけです。"
    Z4 帯: "この線を越えた基準は、それ単独で結論をひっくり返せます。→ 基準1"
```

**発生頻度(全数探索で正直に測り直したもの):**

```
──────── N-1  発生頻度の正直な再測定(第2基準を固定しない全数探索) ────────
  検査した有効入力: 4743210
  L1・L2 が矛盾する入力: 389434 件 (8.210%)
    うち「どちらかの基準で2案が同点」の入力: 389434
    うち 完全に非同点の入力            : 0
  参考: 「どちらかの基準で同点」の入力は全体の 26.0%
```

> **測定の但し書き(自己批判):** 初回の測定では第2基準を意図的に同点固定したまま集計してしまい 41.04% という数字が出た。これは母集団の作り方が偏っており不当なので破棄し、上記の全数探索(4,743,210 件)で測り直した。**正しい頻度は 8.21%** である。ただし内訳の通り、これは「どちらかの基準で2案が並ぶ」入力(全体の 26.0%)に集中しており、その部分集合の中では約 3 件に 1 件で起きる。「価格は同じ、機能で差がつく」は現実の比較で最も普通の形であり、稀なケースではない。

なお完全非同点でも、探索すれば発生する(ランダム探索 30 万試行で検出):

```
──────── N-3  非同点でも矛盾するか(現実的な入力の代表例) ────────

```

**なぜテストが見逃したか:** `tests/tenbin.test.js` は AC-11(`winContrib` の値)と AC-05/AC-07(`criticality` の値)を**別々の test で**検証している。両者が矛盾しないことを見る表明が1本も無い。AC-12 は「相互検算に価値がある」と明記していたが、テストはコア内の `g_k ≤ 1` と `tippingPoint` を突き合わせており、**L2 が独自に持っている `v > 1` は検証範囲の外**にある。性質テスト P-2 も `Σg = 1` しか見ていない。

**修復提案:**

L2 に判定を持たせないこと(INV-2「L2 は計算しない」)。**`crosses` の真偽を L1 が確定させて ViewModel に載せる。** design §1-4 の D-1(「表示文字列まで L1 が確定させる」)と同じ理屈が、真偽値にもそのまま当てはまる。

```js
// L1 winContribution() 内、Contribution に1フィールド足す
//   crossesUnity: (w[j] * (a[W][j] - a[L][j])) > (d0 + EPS)   ← E-4 と同一式・同一 EPS
// L2 は index.html:2180 を次に置き換える
if (g.crossesUnity) { node.classList.add("crosses"); crossed.push(g.name); }
```

`tippingPoint` の `down` と**同一の式・同一の EPS** を使うことが要点である。値を再計算するのではなく、判定の根拠を1箇所に集める。あわせて、この整合をテストで固定すること(§6 に表明案を示した)。

### MAJOR-1 — `normalizeWeights` が Σŵ の overflow で事後条件を破り、画面に嘘の数値を出す

**行番号:** `index.html:932-952`(特に `944: if (sum <= EPS)`)

**現象:** design §4-2 の事後条件は `|Σ_j w[j] − 1| ≤ EPS` である。実装は Z-1 / E-9 に従って `sum <= EPS`(下側)を検査するが、**`sum` が `Infinity` に振り切れる上側を検査していない。** `safe[j] / Infinity = 0` となり、全ての重みが 0 になって事後条件を破る。

`analyze` の NaN 遮断(`index.html:1618-1620`)は `Number.isFinite(w[j])` を見るが、**0 は有限なので通過する。** 結果、退化にも落ちず、警告も出ず、**「重み 0.0% / スコア 0.0」という嘘の数字が正常な結論として表示される。**

**再現させた実行出力:**

```
──────── F-1  normalizeWeights の事後条件破れ(overflow) ────────
  ŵ=[1e+308,1e+308] → w=[0,0] Σw=0  事後条件|Σw−1|≤1e-9: false
  ŵ=[1.5e+308,1] → w=[1,6.66666666666667e-309] Σw=1  事後条件|Σw−1|≤1e-9: true
  ŵ=[1e+308,1e+308,1e+308] → w=[0,0,0] Σw=0  事後条件|Σw−1|≤1e-9: false
```

**到達経路の検証(UI からは到達しない / localStorage からは到達する):**

```
──────── R-1  巨大 rawWeight の到達経路(UI 入力 vs localStorage) ────────
  UI からの重み入力経路:
    rail(range, min=0 max=100)  → index.html:2714 Math.max(0,Math.min(100,pct))/100
    weight-num(number)          → index.html:2733 Math.max(0,Math.min(100,v))/100
    to-threshold ボタン         → index.html:2766 Math.max(0,Math.min(1,row.wStar))
  → いずれも clamp 済み。setWeight は reweight の出力×100 を書くので
    rawWeight は [0,100] に収まる。UI からは到達しない。
  localStorage 経由(DevTools / 別タブの旧版 / 手書き JSON):
    migrateState → ok / validateState → ["ok","value"]
    → failed でも repaired でもない = 「正常データ」として起動する
    analyze → ok=false degenerate=tie
    画面に出る重み: ["0.0%","0.0%"]
    画面に出るスコア: ["案X=0.0","案Y=0.0"]
    正しい答え: 重み 50%/50%、スコア 50.0/50.0 の同点
    実際の答え: 重み 0.0%/0.0%、スコア 0.0/0.0 の同点 ← 数値が全部嘘
```

`validateState` は `rawWeight ≥ 0` と有限性しか見ないため、`1e308` を **`repaired` でも `failed` でもなく `ok`** として通す。design §3-6 が「DevTools で書き換える」「別タブの古い版が書く」を明示的に想定した経路であり、防御が求められている段である。

**修復提案:** `normalizeWeights` に上側の検査を足す(1行)。

```js
if (!Number.isFinite(sum) || sum <= EPS) { /* 等重み 1/n を返す */ }
```

あわせて `validateState` で `rawWeight` に上限(例 `1e6`)を課し、超過を `repaired` として丸める。design §8-6「巨大入力」の表に「スコアが `1e308`」は載っているが**重みが載っていない**ため、仕様側にも1行追記を提案する。

### MAJOR-2 — `fmt.*` の「最後の砦」に穴があり、文字列 `"Infinity"` が画面に出る

**行番号:** `index.html:770-772`(`isShowable`)、`776-779`(`signedFixed`)

```js
770:  function isShowable(v) {
771:    return typeof v === "number" && Number.isFinite(v);
772:  }
```

**現象:** design §4-14 は「**`NaN` / `Infinity` を渡された場合は `"—"` を返す**(画面に `NaN` の4文字を出さないための最後の砦)」と定め、§5-6 D-10 は「**画面に文字列 `NaN` が出る経路を1本も残さない**」と宣言している。

`isShowable` は**引数の有限性しか見ていない。** `fmt.score` / `weight` / `weight6` / `points` / `percent` はいずれも内部で `v * 100` してから `toFixed` するため、`v` が有限でも `v * 100` が `Infinity` に振り切れると、`toFixed` は文字列 `"Infinity"` を返す。砦が守っているのは入口だけで、**乗算の後ろが素通しになっている。**

**再現させた実行出力:**

```
──────── F-2  fmt.* が文字列 "Infinity" を返す ────────
  fmt.score(1e+307) = "Infinity"   ← 期待は "—"(design §4-14)
  fmt.weight(1e+307) = "Infinity"   ← 期待は "—"(design §4-14)
  fmt.weight6(1e+307) = "Infinity"   ← 期待は "—"(design §4-14)
  fmt.points(1e+307) = "+Infinity"   ← 期待は "—"(design §4-14)
  fmt.percent(-1e+307) = "-Infinity"   ← 期待は "—"(design §4-14)
```

**到達経路の検証(`initialWeights` は範囲検査を受けない):**

```
──────── R-2  画面に文字列 "Infinity" が出る到達経路 ────────
  validateState → ["ok","value"] (initialWeights.c1 = 1e+307)
  weights[0].displayInitial = "Infinity"
  Z5 に出る <li> の textContent(index.html:2252):
    "最初の重み: 価格: Infinity%  →  現在: 35.0%"
  → design §4-14「NaN/Infinity を渡された場合は — を返す」の反例。
    isShowable(index.html:770)は引数の有限性しか見ず、×100 後の overflow を見ていない。
  最小修正例の確認: (v*100) の有限性も見れば防げる:
    safeWeight(1e307) = "—" / safeWeight(0.35) = "35.0"
```

`validateState`(`index.html:1465-1483`)は `initialWeights` の各値に `Number.isFinite` しか掛けず、**`[0,1]` の範囲検査をしていない。** そのため `1e307` が `ok` として通り、`index.html:1592` の `fmt.weight(iw)` を経て `index.html:2252` で `<li>.textContent` に入る。

**修復提案:** 砦を乗算の**後ろ**に移す(上の実行出力で最小修正が有効なことは確認済み)。

```js
function isShowable(v) {
  return typeof v === "number" && Number.isFinite(v) && Number.isFinite(v * 100);
}
```

あわせて `validateState` で `initialWeights` の各値を `[0,1]` に範囲検査し、外れたら `initialWeights = null`(design §3-6 が既に定めている「キーが現在の基準と不一致 → null」と同じ扱い)にする。

### MAJOR-3 — 同点(tie)なのにグリッドで1行だけが勝者としてハイライトされる

**行番号:** `index.html:2361`、`index.html:2366`

```js
2361:  var winnerId = vm.winner ? vm.winner.id : null;
...
2366:  cls(tr, "is-winner", o.id === winnerId);
```

**現象:** `renderRanking`(`index.html:1994`)は `tied` を正しく見て、同点時に勝者ハイライトを抑止している:

```js
1994:  var isWinner = (r.rank === 1 && !tied && vm.ranking.length >= 2);
```

ところが `renderGrid` の同じ判定(`index.html:2366`)は **`tied` を見ていない。** `analyze` は tie のときも `winner` を非 null で返す(design §4-13「`ok = false` でも計算できる部分は計算する」に従った正しい挙動)ため、**同点なのにグリッドの1行だけが勝者として強調される。**

AC-18 は「同点のとき頑健性ラベルと `g_j` を表示してはならない」と定めており、勝者ハイライトは明示的な禁止対象ではない。しかし FR-19 / prd §5-3 が同点時に「同点です。基準またはスコアを見直してください」と表示させる意図は、**どちらが勝ちか決まっていないと伝えること**にある。片方だけを視覚的に勝者として強調するのは、その意図を正面から損なう。**同じ画面の順位表(Z2)は同点を正しく表現しているのに、グリッド(Z6)だけが勝者を1つ選んでいる**という不整合でもある。

## 6. テストが見ていない領域(この先壊れ得る場所)

### 6-1. 【最重要】L1 と L2 が**同じ判断を二重に持っている**箇所

BLOCKER-1 と MAJOR-3 は、症状は違うが**同じ構造の欠陥**である:「ある判断が L1 と L2 の両方に書かれ、片方だけが正しい」。

| 判断 | L1 の実装 | L2 の実装 | 状態 |
|---|---|---|---|
| 単独で逆転可能か | `tippingPoint` の `down`(`1034`、EPS 付き) | `v > 1`(`2180`、EPS 無し) | **矛盾する(BLOCKER-1)** |
| 勝者を強調してよいか | `rank().tied`(`1015`) | `1994` は見る / `2361` は見ない | **片方だけ正しい(MAJOR-3)** |
| 「最も浅い」基準 | `robustness.kStarId`(`1228`) | `i === 0`(`2129`) | 現状一致(criticality が昇順のため)。**並び順の規則が変わると静かに割れる** |

現行のテストは L1 の出力しか見ないため、**この類型の欠陥は原理的に検出できない。** 対策は2つあり、両方を推奨する:

1. **判断を L1 に集約する。** 真偽値も ViewModel に載せる(D-1 の論理を数値以外にも広げる)。
2. **L1 の出力どうしの整合を表明するテストを足す。** これは DOM 無しで書ける:

```js
// AC-12 の相互整合を「同一 analyze の出力どうし」で表明する
test("整合: winContrib の g>1 と criticality の下方向逆転可能が一致する", () => {
  // ランダム試行 + 「ある基準で2案が並ぶ」を必ず含む入力を混ぜること
  for (const st of casesIncludingTiedCriterion()) {
    const vm = core.analyze(st);
    if (!vm.ok) continue;
    for (const g of vm.winContrib) {
      const row = vm.criticality.find(r => r.criterionId === g.criterionId);
      const l1Down = !row.infeasible && row.delta < 0;
      assertEqual(g.crossesUnity, l1Down, "基準 " + g.name);
    }
  }
});
```

**この表明を書いていれば BLOCKER-1 は実装時点で赤くなっていた。**

### 6-2. 「ある基準で2つの選択肢が並ぶ」入力が、テストデータに1つも無い

DS-1 / DS-2 / DS-3 のいずれも、**全ての基準で全ての選択肢が異なる値**を持つ。ところが実測では、この「同点の列」こそが `g_j = 1` や `w_k d_k = D₀` といった**境界ちょうど**を生む源だった(N-1 の測定で、矛盾の 389,434 件すべてがこの family に属した)。

「価格は同じ、機能で差がつく」は現実の比較で最も普通の形である。**境界を踏む入力が正典データセットから構造的に除外されている。** DS-1 の変種として「1基準だけ同点」のデータセットを AC に足すことを提案する。

### 6-3. localStorage 経由で入る「有限だが極端な値」

MAJOR-1 / MAJOR-2 はいずれもこの経路だった。テストの AC-22 は「壊れたデータの復旧ラダー」を検証しているが、検証しているのは**構造的に壊れたデータ**(型違い・欠損)であり、**型は正しいが値が極端なデータ**(`1e308`、`1e307`)は含まれていない。

`validateState` の検査は概ね「型 + 符号 + 有限性」で止まっており、**上限**を見ていないフィールドが複数ある:

| フィールド | 下限 | 上限 | 状態 |
|---|---|---|---|
| `rawWeight` | ✅ `>= 0`(`1382`) | ❌ 無し | **MAJOR-1 の入口** |
| `initialWeights[*]` | ❌ 無し | ❌ 無し | **MAJOR-2 の入口** |
| `cutoff` | ✅ 0(`1390`) | ✅ 10(`1391`) | 良い |
| `theta` | ✅ 0(`1447`) | ✅ 1(`1447`) | 良い |
| スコア | ✅ 0(`1344`) | ✅ 10(`1345`) | 良い |

`cutoff` / `theta` / スコアが上下限とも守られているのに、**重み系だけが上限を持たない。** ここは仕様(design §3-6 の `repaired` 表)にも重みの上限が書かれておらず、仕様と実装が揃って抜けている。

### 6-4. `analyze` の入力が `validateState` を通っている保証が無い

design §4-13 の事前条件は「`state` は `validateState` を通過済み」だが、L3 の `draw()`(`index.html:2569`)は `state` をそのまま `analyze` に渡す。起動時(`3058`)は `TenbinPersist.load()` 経由で `validateState` を通るが、**その後の UI 操作で変化した `state` は再検証されない。**

現状は UI 側の clamp(`2714/2733/2766/2794/2830`)が事前条件を代行しているため実害が無いことを実測で確認した(MINOR-3 参照)。しかし**防御が呼び出し側に散在している**状態であり、新しい入力経路(ペースト、インポート、URL パラメータ等)が1つ増えれば破れる。design §8-6 が「全て入口の `validateState` で正規化してから state に入れる」と書いた原則が、実装では守られていない。

### 6-5. 丸め境界(`.x5`)の振る舞い

design §5-3 は「丸め境界での方向は仕様に含めない」と明記し、AC の期待値29個がこの境界に乗らないことを実測で確認している。これは**正しい割り切り**である。ただし裏を返せば、ユーザーの任意入力で `21.85 → 21.9` / `63.55 → 63.5` のような直観に反する丸めは**普通に起きる**。テストは AC の29個しか見ていないため、この領域は完全に未検証のまま残る。FR-10 が「必ず逆転相手の名前と理由文を併記」させる設計になっているので実害は小さいが、**ここは仕様として意図的に空白であることを、次の位相に申し送るべき**である。

### 6-6. 5件の SKIP はすべてブラウザ実機を要する

`AC-22`(リロード復元・全消去後のキー0個)、`AC-23`(実ファイル3本)、`AC-24`(ダブルクリック起動)、`AC-25`(Network リクエスト数=1)、`AC-26`(キーボード7操作・ズーム200%)。**これらは Node のコア抽出では原理的に検証できない**ため、SKIP は正しい判断である。ただし本レビューの範囲外でもある。特に次の2点は実機確認を強く推奨する:

- **AC-26 のキーボード操作。** `renderCriticality` の `appendChild` による並べ替え(`2139`)は D-13 に従ってフォーカスを保つ設計だが、**並べ替えが起きた瞬間に Tab 順序が変わる**。「閾値へ」ボタンを押した直後に行が移動するため、キーボード利用者が意図しない位置にフォーカスを持っていかれる可能性がある。並べ替えを `change`/`blur` 時のみに限定している(`2595`)のは正しい緩和だが、実機での確認が要る。
