# 天秤 (Tenbin)

> 勝った選択肢を出すのではなく、**その勝ちがどの基準の重みを何ポイント動かすと崩れるか**を答える、単一HTMLの意思決定ツール。

---

## これは何か

複数の選択肢を、重み付きの基準で採点して順位を出す道具は「加重決定マトリクス」と呼ばれ、無料のものが山ほどある。天秤もその計算はする。だが天秤の一次出力は順位ではない。画面を開いて最初に読めるのは、たとえばこういう一文である。

> ベンダーB の1位は、移行コストの重みを 15.0% から 21.8%(+6.8ポイント)に動かすと ベンダーA に入れ替わります。他の 1 個の基準では単独で逆転しません。価格を 26.4% まで下げても同じことが起きます。機能充足度を 48.1% まで上げても同じことが起きます。サポートの重みは単独では結論を変えません。

なぜこれを作ったか。`findings.md` の実地調査(13製品を実際に開いて確認)で、市場がきれいに二分されていることが分かったからだ。感度分析——「重みを動かしたら結論はどうなるか」を数値で示す機能——を持つのは、1000minds($25,000/年、無料枠なし・必ず商談)、TransparentChoice(第三者サイト掲載で £4,000/年〜)、SpiceLogic(Windowsデスクトップ買い切り)といった高額商用層だけ。無料Web層(geratools、altftool、chamsdel、onlinetoolhubs、Argumentree ほか)は、加重和と順位を出して終わる。ClickUp / Notion のテンプレート型に至っては重みの合計計算すら手動運用である。**中間が存在しない。**

唯一の例外が yesnowheelapp の "Tipping Point Check" で、これは「Location の重みを 8.5 ポイント上げれば勝者が逆転する」と具体値まで出す。天秤の設計参照点はここにある。ただし yesnowheelapp は単一基準の逐次検査に留まり、貢献度%も保存も持たない。天秤は **全基準 × 全挑戦者を総当たり**で解き、勝ち幅の内訳(貢献度)を出し、localStorage に保存し、CSV / Markdown / JSON で書き出す。TransparentChoice が自社FAQで「加重スコアリングは数学的厳密性と整合性チェックを欠く」と述べて厳密性を有料層の対価に据えているのに対し、天秤は感度分析を無料・登録不要・ブラウザ内完結で降ろす。それがこの製品の立ち位置である。

## 使い方

**`index.html` をダブルクリックするだけ。** インストールもビルドもログインも要らない。ファイル1個で完結し、ネットワークに一切触れない。

1. **基準を入れる。** 「基準を足す」で、何で比べるかを決める(価格、機能、サポート…)。各基準には重み(0〜100%)と向き(「高いほど良い」/「低いほど良い」)を設定する。価格や移行コストのように**低いほど良い**ものは「低いほど良い」に切り替える。重みは1つ動かすと残りが自動で比例配分され、合計は常に厳密に100%に保たれる。基準は3〜6個が推奨(7個目で「重複していないか」の警告、上限10個)。
2. **選択肢を入れる。** 「選択肢を足す」で、比べたいものを2つ以上足す。こちらも推奨2〜6件、上限10件。
3. **採点する。** 選択肢 × 基準のグリッドに 0〜10 で点を入れる(0.5刻み)。1セル埋めるごとに全部が再計算される。「計算」ボタンは存在しない。未入力セルが残っている間は「未入力のセルが N 個あります。埋めるまで結論は出せません。」と表示され、結論は出ない。
4. **結論を読む。** 画面上部の「結論」に、頑健性ラベルと上記の一文が出る。その下に順位、左に「基準 — 崩れやすい順」、右に「なぜ勝ったか」が並ぶ。

## 画面の見方

### 頑健性ラベル — robust / contingent / fragile

結論の脇に必ず出る3段階の判定。**ラベルだけが単独で表示されることはなく、常に生の数値 Δ\*(デルタスター)とセットで出る。**

| ラベル | 意味 | 表示される文 |
|---|---|---|
| **robust** | どの単一基準の重みを 0%〜100% のどこに動かしても1位は入れ替わらない | `robust — どの単一基準の重みを動かしても結論は変わりません(Δ* = 逆転不能)` |
| **contingent** | 逆転はできるが、しきい値 θ より大きく重みを動かす必要がある | `contingent — 結論は重みの置き方に依存します(Δ* = 6.8ポイント > しきい値 5.0ポイント)` |
| **fragile** | θ 以下のわずかな重みの差で結論が崩れる | `fragile — 結論はごく僅かな重みの差で崩れます(Δ* = 6.8ポイント ≤ しきい値 10.0ポイント)` |

robust のときは必ず但し書きが添えられる: **「基準そのものが抜けている可能性は、この分析では検出できません。」** robust は「この重みの下で結論が安定している」という意味であって、「基準の選び方が正しい」という意味ではないからだ。

θ(しきい値)は画面上部から変更できる。**θ を変えてもラベルは変わるが、Δ\* の値と k\*(最も崩れやすい基準)は変わらない。** 上の表の contingent と fragile は同じ入力(Δ\* = 6.8pt)で、θ を 10pt から 5pt に下げただけである。

### 逆転閾値 — 「基準 — 崩れやすい順」の読み方

各基準の行に、こう出る。

```
移行コスト   現在 15.0% → 逆転 21.8%(+6.8ポイント) ベンダーA に逆転
価格         現在 35.0% → 逆転 26.4%(-8.6ポイント) ベンダーA に逆転
機能充足度   現在 30.0% → 逆転 48.1%(+18.1ポイント) ベンダーA に逆転
サポート     逆転不能
```

**逆転閾値とは、「その基準の重みをどこまで動かせば、今の1位が入れ替わるか」の境界値である。** 符号は方向を表す。`+6.8` は上げれば逆転、`-8.6` は下げれば逆転。並び順は変化量の絶対値の昇順で、**上にあるほど結論を握っている基準**。逆転不能な基準は末尾に理由付きで置かれる。

行の「21.8% へ」ボタンを押すと、実際にその重みに設定される。すると画面上で本当に同点になる。これは仕様として保証されている(下記「仕組み」の検算参照)。

**この画面の最も重要な点**: 上の例で最上位に来ているのは、最も重みの**小さい**基準(移行コスト 15%)である。最も重みの**大きい**基準(価格 35%)より上にいる。「重みが大きい基準ほど重要」は直感的だが、常には成り立たない。Triantaphyllou & Sánchez (1997) が「最も重みの小さい基準が最も重大でありうる」と示していることが、実データで起きている。

### 貢献度が100%を超えるのはなぜか

**ここは実際に混乱する箇所なので、先に読んでほしい。**

「なぜ勝ったか」に出る**勝敗貢献度**は、DS-1 でこうなる。

| 基準 | 貢献度 |
|---|---|
| 価格 | **+300.0%** |
| 機能充足度 | −85.7% |
| サポート | +57.1% |
| 移行コスト | −171.4% |
| **合計** | **100%** |

価格が 300% ある。合計は 100% になる。おかしく見えるが、正しい。

**分母が「総合スコア」ではなく「勝ち幅」だからだ。** この分解が答えているのは「ベンダーB のスコアの内訳は?」ではなく「**ベンダーB はなぜベンダーA に勝てたのか?**」である。分母は勝ち幅 D₀ = 67.0 − 63.5 = **3.5ポイント**しかない。この 3.5 ポイントを 100% として、各基準がそこにいくら足し、いくら引いたかを表している。

読み方はこうだ。ベンダーB は価格で大差をつけ、勝ち幅の 3倍(300%)を稼いだ。しかし機能充足度で 85.7% を、移行コストで 171.4% を吐き出している。差し引きで手元に残ったのが 100%、すなわち 3.5 ポイントだった。**負の貢献度は「勝者がその基準では負けている」ことを意味し、逆符号のバーで描かれる。**

これは加重和が**補償型**であること——ある基準の好成績が別の基準の悪成績を埋め合わせること——を、隠さず画面の中央に出したものである。UK政府 Analysis Function の MCDA ガイドが注意点として挙げているまさにその性質が、数字としてそのまま見えている。

そして 100% の線には意味がある。**貢献度が 100% を超えた基準は、それ単独で結論をひっくり返せる。** 画面にも「この線を越えた基準は、それ単独で結論をひっくり返せます。→ 価格」と出る。上の例で 100% を超えているのは価格だけで、実際「基準 — 崩れやすい順」で価格は「26.4% まで**下げる**と逆転」となっている。逆に 100% 以下の基準(サポート +57.1%)は重みを下げても逆転させられない。この一致は偶然ではなく、代数的な恒等式である(後述)。

なお「各選択肢のスコアの内訳」に出るもう一方の貢献度(**スコア貢献度**)は分母が総合スコアなので、こちらは 0〜100% に収まり合計 100% になる。ベンダーB なら 価格 31.3% / 機能充足度 35.8% / サポート 23.9% / 移行コスト 9.0%。2つは別物である。

## 仕組み

### 加重和

入力は 0〜10 の生スコア `raw_ij` と、基準ごとの向き `dir_j`、重み `ŵ_j`。

```
正規化:  a_ij = raw_ij / 10            (dir_j = benefit「高いほど良い」)
         a_ij = (10 − raw_ij) / 10     (dir_j = cost   「低いほど良い」)
         w_j  = ŵ_j / Σ_j' ŵ_j'         (常に Σ w_j = 1)

スコア:  S_i = Σ_j w_j · a_ij           画面表示は S_i × 100
```

コスト反転に逆数(1/x)ではなく補数(10 − x)を使っているのは意図的である。逆数は非線形で、後述の閉形式が成立する前提を壊す。また正規化に min-max(選択肢集合内の最大最小で割る方式)を使っていないのも意図的で、min-max だと選択肢を1件足しただけで既存選択肢のスコアが動き、順位が入れ替わりうる。**天秤の `a_ij` は他のどの選択肢にも依存しないため、選択肢を追加・削除しても既存選択肢どうしの相対順位は構造的に変わらない。**

### 逆転閾値の式

基準 k の重みだけを `w_k → x` に動かし、他は比例再正規化する(これは画面のスライダーの挙動と同一の写像である)。

```
w_j(x) = w_j × (1 − x) / (1 − w_k)     (j ≠ k)
w_k(x) = x                              Σ_j w_j(x) = 1 を常に満たす
```

勝者 W と挑戦者 L について、勝ち幅 `D₀ = S_W − S_L`、基準 k での勝者の優位 `d_k = a_Wk − a_Lk` と置くと、差 `D(x) = S_W(x) − S_L(x)` は x の一次分数式になり、`D(x*) = 0` を解いて閉じた形が出る。

```
                 D₀ · (1 − w_k)
        Δw_k = ──────────────────          新しい重み w_k* = w_k + Δw_k
                   D₀ − d_k

逆転可能 ⟺  d_k < 0(上げて逆転)  または  w_k · d_k > D₀(下げて逆転)
支配的優位(逆転不能) ⟺  d_k ≥ 0  かつ  w_k · d_k ≤ D₀   →  Δw_k = ∞
```

分子 `D₀(1 − w_k)` は常に正なので、**符号は分母 `D₀ − d_k` だけで決まる**。そして `w_k` は分子に `(1 − w_k)` としてしか現れず効果は高々 (1−w_k) 倍だが、`d_k` は分母に直接入り、大きく負であるほど `Δw_k` を急速に小さくする。だから**重みが小さくてもスコア差が大きい基準は、重みが大きくスコア差の小さい基準より critical になりうる**。反直感的な結果は、この分母項が生んでいる。

貢献度も同じ量の別の顔である。勝敗貢献度 `g_j = w_j · (a_Wj − a_Lj) / D₀ = w_j · d_j / D₀` について `Σ_j w_j d_j = S_W − S_L = D₀` なので合計は恒等的に 1。そして支配的優位条件 `w_k d_k ≤ D₀` は `g_k ≤ 1` と**同値**である——「その基準ひとつで勝ち幅の全部を説明できない限り、その基準を捨てても勝者は変わらない」。これが「100% の線を越えた基準は単独で逆転できる」の正体である。

### 実例(DS-1)

`prd.md` の基準データセット DS-1 は、3社のベンダー選定。

| 基準 | 向き | 重み | ベンダーA | ベンダーB | ベンダーC |
|---|---|---|---|---|---|
| 価格 | **cost** | 35% | 7 | 4 | 6 |
| 機能充足度 | benefit | 30% | 9 | 8 | 8 |
| サポート | benefit | 20% | 7 | 8 | 5 |
| 移行コスト | **cost** | 15% | 2 | 6 | 8 |

正規化(コスト2基準が反転する)と加重和で、**ベンダーB = 67.0 / ベンダーA = 63.5 / ベンダーC = 51.0**。勝者はベンダーB、勝ち幅 D₀ = 3.5 ポイント。ちなみに反転を忘れて全部 benefit にすると A=68.5 / B=63.0 / C=67.0 で**勝者がベンダーA に変わる**。向きの設定は結論に実効的に効く。

移行コストの閾値を式に入れてみる。`D₀ = 7/200`、`d = a_B,移行 − a_A,移行 = 2/5 − 4/5 = −2/5`、`w_k = 3/20`。

```
Δw = (7/200)(1 − 3/20) / (7/200 − (−2/5)) = (119/4000) / (87/200) = 119/1740 = +0.0683908…
w* = 3/20 + 119/1740 = 19/87 = 21.839080…%
```

画面表示は `+6.8ポイント`、`21.8%`。ここまで動かすと何が起きるか。比例再正規化後の重みは 価格 32.183908% / 機能充足度 27.586207% / サポート 18.390805% / 移行コスト 21.839080%(合計は厳密に 1)、そして総合スコアは **ベンダーB = 64.8、ベンダーA = 64.8** で**厳密に同点**になる。天秤はこの状態を「同点です。基準またはスコアを見直してください。」と表示し、頑健性ラベルを出さない。

4基準の結果をまとめると:

| 基準 | 重み | Δw_k | 逆転する重み | 逆転相手 |
|---|---|---|---|---|
| 移行コスト | 15.0% | **+6.8pt** | 21.8% | ベンダーA |
| 価格 | 35.0% | **−8.6pt** | 26.4% | ベンダーA |
| 機能充足度 | 30.0% | **+18.1pt** | 48.1% | ベンダーA |
| サポート | 20.0% | **逆転不能** | — | — |

Δ\* = 6.8pt、k\* = 移行コスト。既定の θ = 10pt に対し 6.8 ≤ 10 なので **fragile**。サポートが逆転不能なのは、両方の挑戦者に対して `d_k ≥ 0` かつ `w_k·d_k ≤ D₀` だから(vs A: 0.02 ≤ 0.035、vs C: 0.06 ≤ 0.16)。実際、サポートの重みを 0% にしても 100% にしても1位はベンダーB のままである。

## 何をしないか

**ネットワークに一切触れない。** `fetch` / `XMLHttpRequest` / `sendBeacon` / `WebSocket` / `EventSource` / `<form action>` の出現回数はソース全体で **0 回**(実測)。`<script src=`、`<link rel="stylesheet"`、`@import`、`http://` `https://` で始まるリソース参照も **すべて 0 回**。フォントもチャートライブラリもアイコンも外から取らない。描画は CSS と inline SVG だけで行っている。

**ログインもアカウントもない。** サーバが存在しない。データはブラウザの `localStorage` にだけ入り、キーはすべて `tenbin.v1.` で始まる名前空間に閉じている。全消去ボタンでいつでも消せる。この事実はフッタに常時表示されている:「このページのデータは、あなたのブラウザにだけ保存されています。どこにも送信していません。」

v1 で**意図的に**作らなかったもの:

| 作らなかったもの | 理由 |
|---|---|
| **AHP のペア比較と整合性比率 (CR ≤ 0.1)** | 差別化としては強い(高額商用ツールの独占領域)が、実装に必要な Random Index テーブルが調査で確認できたのは n=3 の RI=0.58 ただ1つ。基準上限10に対し n=4〜10 の値を独自に持ち込むことになる。加えて閾値 0.1 自体に文献上の留保が3重にかかっている(Saaty の n=3/n=4 追加提案の表記揺れ、基準数増加時の超過批判、CR<0.2 許容の立場)。この根拠状態で「0.1 超で赤く警告」を断定的に出すべきではないと判断した |
| **結果の永続URL共有** | サーバなし制約で実現できない。代わりに localStorage 保存 + CSV / Markdown / JSON エクスポートで「記録として残す」ニーズに応えている |
| **AI による選択肢・基準・スコアの自動生成** | AI生成のスコアは根拠が追跡できず、「なぜその結論か」を示すという天秤の目的と正面から衝突する。ネットワーク送信ゼロとも両立しない |
| **TOPSIS / ELECTRE などの手法切替** | 一般利用者には手法選択自体が認知負荷。加えて TOPSIS の近接係数は重みに対して非線形で、逆転閾値が閉形式で解けない——中核機能と技術的に衝突する |
| **Monte Carlo / 確率的感度分析** | 決定論的な重みスイープで「どの基準が支配的か」は十分に答えられる |
| **多階層のサブ基準ツリー / 多人数の共同編集・投票 / PPM連携** | それぞれ既存の成熟製品の主戦場であり、個人の意思決定という中核価値と直交する |
| **スケール選択(0-5 / 0-7 / 0-10 の切替)** | 尺度を定数倍しても加重和の順位は変わらないので、選択肢を提供する実利がない |

## 限界と正直な断り書き

**★ ここは飛ばさずに読んでほしい。天秤が自分について隠していないことを、README でも隠さない。**

### 1. θ = 0.10 は経験則であり、理論的な裏付けを持たない

fragile / contingent を分けるしきい値 θ の既定値 10 ポイントには、**論文の裏付けが一切ない**。由来は、既存ツール yesnowheelapp が「8.5 ポイントのシフトで逆転する」事例を「7.4 対 7.1 で決着した判定ではなく、真に僅差の決定である」と総括したこと——その観測された唯一の実例を fragile 側に含める、最小の切りの良い値が 10 ポイントだった。それだけである。

天秤は、無料ツール chamsdel の「2案が5点差以内なら僅差」というルールを「経験則で理論的裏付けなし」と批判している立場にある。ならば自分の閾値を裏付けありと偽ってはならない。だから θ は**ユーザーが変更可能**で、画面のツールチップには「しきい値 10 ポイントは経験則であり、理論的な裏付けはありません。ご自身の判断で変更できます。Δ\* と k\* は θ に依らず不変です。」と書いてある。**ラベルは主観的な線引きだが、Δ\* の数値は客観的である。** ラベルが単独で表示される画面は1つもない。

### 2. 貢献度の分解式には、一次資料の裏付けが確認できていない

「総スコア `Σ_j w_j·a_ij` に対して各項 `w_j·a_ij` が占める割合が貢献度である」——この分解式そのものを明記した一次学術資料は、調査では**見つけられなかった**。確認できたのは、SpiceLogic が weighted criteria attribute chart として製品化していること、onlinetoolhubs が加重総和を MAUT の線形結合と記述していること、そこまでである。

勝敗貢献度 `g_j` は、これを勝ち幅の差分に適用しただけの代数的恒等式で、`Σ_j g_j = 1` は自明に成り立つ。だが数学的に自明であることと、その指標が意思決定手法として学術的に検証されていることは別である。だから画面には常にこう添えてある: **「この分解は、加重和の各項が総和に占める割合を示すものです。学術的に検証された指標ではありません。」**

### 3. 加重和は補償型であり、そこに弱点がある

天秤の中核は加重和(WSM / SAW)である。UK政府 Analysis Function の MCDA 入門ガイドは、これを "classic compensatory MCDA" と呼び、**ある基準の好成績が別の基準の悪成績を埋め合わせてしまう**性質を明示的な注意点として挙げている。同ガイドの対策の示唆は「各基準に絶対的な最低ラインを設け、分析前に選択肢を除外する」こと。

天秤の対応は3つ。(a) 基準ごとに任意の**最低ライン(足切り値)**を設定でき、下回る選択肢は加重和の**前段**で除外され、「移行コストが最低ライン3.0を下回るため除外」と理由が表示される。(b) ただし既定では設定されない任意機能である。(c) そして何より、**勝敗貢献度が補償の実態をそのまま可視化する**——「価格 +300%、移行コスト −171%」という表示は、まさに価格の好成績が移行コストの悪成績を埋め合わせている、その数値そのものである。補償性を隠さず、画面の中央に出している。

それでも、補償型であること自体は消えない。「1つの基準で致命的に劣っていても、他で埋め合わせれば勝ててしまう」という性質は残る。最低ラインを使うか、貢献度の負のバーを自分の目で見て判断してほしい。

### 4. robust は「基準が正しい」という意味ではない

robust は「今ある基準と今の重みの下で、単一基準の重みをどう動かしても1位は変わらない」という意味に過ぎない。**そもそも重要な基準が抜け落ちていることは、この分析では検出できない。** 画面の robust 表示には必ずこの但し書きが付く。

### 5. その他

- 検出できるのは**単一基準の重み変更**による逆転だけである。複数基準を同時に動かした場合の逆転は計算していない。
- 「結論ありき逆算の検知」(重みを編集する間に1位が3回以上入れ替わったら警告)は**警告であって禁止ではない**。編集をブロックしない。止められるのは自分自身だけである。
- 天秤は助言をしない。順位も頑健性も、あなたの代わりに決めるものではない。

### 抽出可能コアブロックの仕組み

`index.html` は単一ファイルだが、**計算コアだけを外部から取り出して実行できる**。単一HTML制約とテスタビリティを両立させる仕掛けである。

```html
<script id="tenbin-core">
/*===TENBIN-CORE-BEGIN===*/
...  計算コア(1,010行 / 37,442文字)...
const TenbinCore = Object.freeze({ VERSION, EPS, normalize, ... analyze, ... fmt, TEXT });
/*===TENBIN-CORE-END===*/
globalThis.TenbinCore = TenbinCore;
</script>
```

テスト側は HTML をテキストとして読み、この2つのマーカで囲まれた領域を切り出して `new Function()` で評価し、返ってきた `TenbinCore` に対してテストを回す。ブラウザも DOM も要らない。

抽出が成立するために、コア領域には**契約**が課されている(すべてテストで検証される)。

| 契約 | 内容 |
|---|---|
| C-1 | BEGIN / END マーカがファイル中にちょうど1個ずつ、正しい順序で存在する |
| C-2 | マーカが `<script id="tenbin-core">` ブロックの**内側**にある |
| C-3/C-4 | 切り出した領域が単体で評価でき、`TenbinCore` が `Object.freeze` されたオブジェクトとして返る |
| C-5/C-6 (INV-1) | コア領域が `document` / `window` / `localStorage` / `sessionStorage` / `navigator` / `fetch` / `XMLHttpRequest` / `alert` / `Date` / `globalThis` / `Math.random` / `</script` を**一切参照しない** |

つまりコアは**純粋関数の層**である。外部を読まず、副作用を持たず、例外を投げない(`analyze` は最悪でも退化状態を返す)。ファイル内の残り3つの `<script>` ブロック(`tenbin-persist` / `tenbin-render` / `tenbin-store`)が localStorage・DOM・イベントを担当し、コアには一方向にしか依存しない。だから DS-1 を入れれば、ブラウザで動かしても Node で `analyze()` を直接呼んでも、ビット単位で同じ値が出る。

公開 API は 21 個:

```
VERSION, EPS,
normalize, normalizeMatrix, normalizeWeights, reweight, computeScores, rank,
tippingPoint, criticality, scoreContribution, winContribution,
robustness, anchoringDetect, applyCutoffs,
analyze, validateState, migrateState, createInitialState,
fmt, TEXT
```

`analyze(state)` が単一の入口で、上の README に出てくる値(`ranking` / `d0` / `criticality` / `winContrib` / `robustness` / `anchoring` / `excluded` / `warnings`)をすべて含む1つのビューモデルを返す。
